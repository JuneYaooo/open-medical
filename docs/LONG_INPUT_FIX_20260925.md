# 长输入分片与自动压缩修复 · 2026-09-25

## 问题与此前测试盲点

用户报告“当前指令或单条输入过大，无法在保留原文的情况下压缩”。该问题成立：此前的历史压缩保护全部当前任务输入，保护区过大时直接拒绝；测试还把这种拒绝作为预期行为，因此既有全量测试通过并未覆盖“长单条输入应自动处理”的产品要求。

沿真实UI链路继续验证还发现：

1. 首页textarea设置12000字符上限，粘贴长输入会在浏览器侧被截短。
2. 核心与医疗会话桥接层有多处20000字符入口限制，项目UI也单独限制20000字符。
3. 医疗桥接层在运行前用系统提示、输入和资料总字符数作预检，超预算直接失败，未到达压缩器。
4. 压缩期间新到的长追加指令会跳过压缩，直接触发模型请求前的预算拒绝。

## 修复后行为

- 长任务输入先完整归档，再按实际序列化后的字节预算分片，逐片合并摘要。每片包含原消息索引、起止位置及总长；不把JSON切片伪装成完整工具结果。
- 原文可通过已有 `read_context_archive` 分页读取，沿用工作区、权限和模型身份的访问限制。
- 短的最新补充要求保留原文；系统指令、权限及审批事实不做有损压缩。
- 摘要明确标注有损，并引用原文归档。模型连续输出超长/不完整摘要时有限重试，失败保留原文，不静默截掉用户条件。
- 首次任务、执行中追加以及准备阶段新到的追加指令都执行预算检查及必要的压缩。
- 当前任务正文支持至200000字符；主页不再依靠textarea截断。超过上限明确提示拆分并保留输入；项目任务按正文与附件总长计算。
- 医疗入口仅针对不可压缩的固定系统配置保留提前拒绝，正文进入运行时自动处理。
- UI区分“整理长输入/压缩历史”，完成后显示实际分片数。

自动压缩不是无损编码，也不能让无限输入装入有限模型窗口。原文归档保持完整，给模型的摘要有损；精确事实须按归档核对。超长非文本媒体、固定系统配置过大、模型输出配置不合法、服务错误仍会明确失败。分片最多512片，有取消和有限重试保护。
