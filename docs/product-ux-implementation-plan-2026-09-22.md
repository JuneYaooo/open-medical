# Open Medical：患者管理与 AI 工作台改造方案

版本：1.0 · 2026-09-22  
用途：供产品、设计、前端、后端及编码 Agent 共同使用的实施依据。  
范围：基于当前仓库与本轮 V5 交互原型，整理目标体验、功能优先级、页面规格、数据要求、代码落点和验收标准。

> 产品目标：以院外患者管理和随访为核心，让医生通过界面或自然语言完成患者资料整理、沟通、计划执行与结果追踪；在持续积累的患者资料上发展诊疗辅助和科研。功能应丰富，日常操作应清晰，尤其适合不熟悉复杂软件的医生。
>
> 本文是改造方案，不代表下述能力已全部实现。V5 使用虚构数据和预设对话，不能作为后端接通、真实模型执行或微信自动化已完成的证据。

## 1. 产品原则与范围

### 1.1 三条主线

| 主线 | 医生实际需要回答的问题 | 主要产出 |
| --- | --- | --- |
| 患者管理 | 这个人是什么情况？资料在哪里？最近发生了什么？ | 可读、可追溯、可更新的患者档案 |
| 院外随访 | 今天该处理谁？患者回复了什么？下一步做什么？ | 待办、沟通记录、随访结果、下一次计划 |
| AI 协作 | 能不能直接说出需求，由系统完成查找、整理和操作？ | 带来源的结果、可执行的操作和可恢复的状态 |

诊疗辅助和科研是确定需要的下一阶段能力。P1/P2 表示开发先后，不表示功能可以从产品中删除。已有可用功能应保留访问路径，在新结构中逐步迁移。

### 1.2 必须坚持的设计决定

- 一级业务导航以“患者、随访、科研”为主。辅助诊疗进入患者上下文，不另设一级入口。
- AI 是全局操作入口，贯穿所有页面；同时保留按钮、表单和列表操作，用户无需学习提示词才能使用系统。
- 简洁通过信息层级和渐进展开实现。不能靠删掉病史、检查结果或来源文件来获得简洁。
- 患者页应具备“概况—变化—完整资料—原文”的阅读路径。任何摘要都不能成为查看原文的障碍。
- 每个页面有一个明确主任务；模板配置、模型设置、运行日志等放在二级入口。
- 页面操作和对话操作共用业务动作、校验、权限和持久化结果，避免两套逻辑。
- 原始事实、AI 提取、人工确认、待核对和后续计划必须区分。
- 可视化用于回答具体问题，每张图必须有日期、单位、数据范围和对应记录。

## 2. 当前项目判断与改造取舍

以下是本次源码检查所得，不等于对全部生产流程进行了端到端验证。

| 当前已有基础 | 源码证据 | 下一步处理 |
| --- | --- | --- |
| 患者总览、病史、诊断、用药、过敏、检验、文件来源 | `src/patient-dashboard.jsx` | 保留并拆出稳定阅读组件，补上下文原文阅读 |
| 检验趋势与按项目、单位分组 | `src/patient-dashboard.jsx`、`shared/patient-dashboard.mjs` | 延续规则，增加记录选择、来源跳转和明确空状态 |
| 就诊时间轴，以及概览中另外汇集的产物、随访等时间记录 | `src/patient-dashboard.jsx`、`src/patients.jsx` | 整合成一个患者事件模型，避免同一事件重复出现 |
| 临床资料编辑、revision 校验 | `src/patient-clinical.jsx` | 阅读与编辑分离，局部编辑复用现有保存机制 |
| 患者消息、随访计划、检查与转诊栏目 | `src/patients.jsx`、`src/care-tasks.jsx` | 归入患者上下文与统一待办，保留原能力 |
| 随访模板、任务和执行相关界面 | `src/followups.jsx`、`src/followup-records.jsx` | 默认进入工作队列，模板和调度设置下沉 |
| CSV 分析、描述统计、检验、样本量与去标识处理入口 | `src/research.jsx` | 保留分析能力；研究项目、队列、字段核对需要新增设计与数据支持 |
| 提案与执行基础 | `server/medical/pending-actions.mjs`、`src/patient-proposal.jsx` | 扩展到统一动作契约，避免绕过提案直接改临床资料 |
| macOS 微信桌面桥接代码 | `server/wechat-bridge.mjs` | 核实可用性、会话匹配、发送证据及异常恢复后再接入业务自动化 |
| 医疗领域工具与 Agent 运行基础 | `server/medical/medical-workspace-domain.mjs`、`src/agent-runtime.js` | 增加结构化页面定位、动作结果和上下文绑定 |

### 2.1 当前体验的主要问题

1. **总览与操作混在一起。** 读病历、看产物、改资料、运行 AI 同时竞争注意力。
2. **相同信息分散。** 就诊、消息、产物和随访各有时间信息，缺少统一患者进程。
3. **完整资料与来源脱节。** 从摘要返回文件时容易跳离当前患者或失去阅读位置。
4. **配置占据日常工作入口。** 随访首页更应回答“今天做什么”，配置在需要时再进入。
5. **AI 与工作区缺少稳定的联动协议。** 靠关键词切页可以演示，无法覆盖真实业务操作。
6. **此前原型简化过头。** 少数摘要不能替代完整患者档案；新增内容也不应再次堆成大量同等权重的卡片。

### 2.2 V5 的定位

V5 是布局与交互参考：三项业务导航、连续档案、资料原文阅读器、指标图、患者时间轴、随访进度、AI 三种显示模式。

正式项目不能直接照搬 V5 的全局变量、函数覆盖、示例患者判断和硬编码日期。应将这些体验迁移到 React 组件及真实领域数据。V5 中陈女士资料最完整，不能据此推断所有患者、文件格式或数据状态都已经覆盖。

## 3. P0 / P1 / P2

### 3.1 优先级定义

- **P0：患者管理闭环。** 医生能查清患者情况、找到资料、处理随访、通过 AI 执行相同任务，并在刷新后保留结果。
- **P1：基于管理资料的诊疗辅助与科研。** 提高资料复核、临床证据整理和研究数据形成的效率。
- **P2：复杂协作与规模化。** 多团队、跨机构、高级分析和更灵活的自动化。

### 3.2 功能清单

| 编号 | 功能 | 优先级 | 本阶段完成的具体范围 |
| --- | --- | --- | --- |
| P0-01 | 患者列表与定位 | P0 | 搜索、分组、待处理筛选、打开后返回原列表位置 |
| P0-02 | 完整患者档案 | P0 | 病史、诊断、用药、过敏、检查、联系人、随访及来源 |
| P0-03 | 资料导入与复核 | P0 | 上传、解析进度、识别失败、提取草稿、确认入档、重复处理 |
| P0-04 | 原文阅读 | P0 | 文件列表、搜索、页码/文本定位、摘要与原文对照 |
| P0-05 | 统一时间轴 | P0 | 就诊、检验、用药事件、监测、随访、消息；筛选及来源定位 |
| P0-06 | 基础指标可视化 | P0 | 同项目同单位趋势、血压双序列、原始记录和不足数据状态 |
| P0-07 | 随访工作队列 | P0 | 待处理、等待回复、已完成；分配、处理、补充、重新打开 |
| P0-08 | 计划与任务执行 | P0 | 模板、时间、渠道、内容、下一次任务、暂停与失败处理 |
| P0-09 | 微信基础接入 | P0 | 渠道状态、患者会话绑定、限定范围读取、回复草稿、发送结果记录 |
| P0-10 | 有范围的自动管理 | P0 | 明确授权的固定提醒/模板规则、有效期、频率、暂停、日志；先验收单平台 |
| P0-11 | AI 统一操作入口 | P0 | 核心业务动作均可通过对话触发；上下文、进度、失败恢复、结果定位 |
| P0-12 | AI 显示与 UI 偏好 | P0 | 工作区/半屏/全屏；调整字号、筛选、字段顺序等受支持配置 |
| P0-13 | 状态与数据一致性 | P0 | 持久化、版本冲突、重复动作抑制、跨页面一致更新、患者隔离 |
| P1-01 | 嵌入式诊疗辅助 | P1 | 病程整理、资料矛盾、用药核对、证据检索、结论草稿与引用 |
| P1-02 | 深化院外管理 | P1 | 问卷、依从性、检查/转诊闭环、规则触发后的人工处理流程 |
| P1-03 | 研究项目与队列 | P1 | 研究问题、纳排条件草稿、候选患者、研究编号及入组复核 |
| P1-04 | 科研字段与质量核对 | P1 | 字段定义、来源、缺失、冲突、查询单、数据版本 |
| P1-05 | 科研分析衔接 | P1 | 复用已有统计功能，分析输入快照、方法说明与结果可复现 |

## 4. 全局信息架构

```text
医生工作空间
├─ 患者
│  ├─ 列表 / 分组 / 搜索
│  └─ 患者详情
│     ├─ 完整档案（摘要、趋势、时间轴、详细病史）
│     ├─ 原始资料（文件、搜索、原文阅读）
│     ├─ 沟通与随访（消息、任务、计划、检查与转诊）
│     └─ 诊疗辅助（继承当前患者，P1）
├─ 随访
│  ├─ 工作队列（默认）
│  ├─ 事项详情
│  └─ 计划模板 / 自动管理规则（二级）
├─ 科研
│  ├─ 研究项目（P1）
│  ├─ 队列 / 字段核对（P1）
│  └─ 分析与导出（复用已有能力）
└─ 设置 / 连接 / 模型 / 运行详情（二级）

全局：AI 对话 + 当前患者/研究上下文 + 页面联动
```

业务首页建议进入随访待处理队列；再次打开时可恢复上一次业务位置。不要为了入口新增一个重复统计的“大而全仪表盘”。V5 为评审方便默认打开示例患者，不等同于生产启动策略。

正式患者页建议将现有消息、随访计划、检查与转诊归为“沟通与随访”的二级内容，控制顶层标签数量；迁移时先保留现有深链接，再调整展示标签。

## 5. 患者列表与患者档案

### 5.1 患者列表

默认显示姓名/患者编号、主要管理问题、最近联系、下次随访、待办状态；电话等仅在需要联系时展开。允许调整列，但保存为医生偏好，不改变患者数据。

搜索支持姓名、院内编号及已授权的联系方式。快捷筛选先提供“全部、今天需要处理、等待回复、逾期”；复杂条件收进筛选面板。点击行打开患者详情，返回后保留查询、排序、分页和滚动位置。

空状态必须区分没有患者、筛选无结果、加载失败和权限不足。只有“没有患者”时展示导入/新增入口，不能所有情况都显示“暂无数据”。

### 5.2 患者详情的阅读顺序

| 层级 | 信息 | 设计要求 |
| --- | --- | --- |
| 身份条 | 姓名、编号、年龄/性别、当前患者 | 始终容易识别；不同患者切换明确 |
| 简短概况 | 主要问题、最近变化、待核对事项 | 2–4句；可定位到来源；注明更新时间 |
| 变化区域 | 关键指标、患者时间轴 | 宽屏并排，窄屏纵向；不默认展示十张图 |
| 当前任务 | 本轮随访进度和下一次安排 | 与真实任务状态一致，可进入处理 |
| 详细档案 | 病史、诊断、用药、过敏、检查、随访 | 连续阅读，不强迫反复展开卡片 |
| 原文 | 对应病历、报告、患者消息 | 就地打开；可回到原来位置 |

患者重要的过敏信息应在身份/临床摘要附近可见，同时保留详细记录；“未记录”“尚未核对”“已核对无已知过敏”是不同状态。

### 5.3 各栏目最低内容

| 栏目 | 必须包含 | 交互 |
| --- | --- | --- |
| 病史与诊断 | 主诉/就诊原因、现病史、既往史、家族史、诊断日期、来源 | 查看原文、补充或纠正 |
| 用药 | 药名、剂量、频次、状态、记录时间、信息来源 | 核对当前使用情况、查看历史变更 |
| 检查 | 项目、结果、单位、采样/检查时间、来源；有则显示原报告参考范围 | 切换指标、看历史记录、打开报告 |
| 随访 | 联系对象、时间、渠道、反馈、处理、待办和下次安排 | 处理当前事项、编辑计划 |
| 生活与支持 | 联系偏好、照护人及关系、已有生活史 | 局部补充，缺失保持未知 |
| 资料 | 文件名、类型、日期、解析状态、来源 | 搜索、预览、定位提取内容 |

历史处方出现某药，不等于现在正在服用。记录修订应保留前后版本；AI 不能把未核对的历史药物直接设为当前使用。

### 5.4 原文阅读器

宽屏在档案旁打开，保留选中段落；可用宽度不足时切换为聚焦阅读。关闭后恢复原标签、筛选和滚动位置。

阅读器包含文件名、业务日期、文件页数或文本位置、前后篇、搜索命中、来源位置和“交给 AI 整理”。PDF 保留页码与定位，图片支持放大，文本支持命中高亮。真实文件预览能力需复用和检查 `MaterialDetails`，V5 只演示文字原文。

资料未解析完成时仍允许查看原文件；显示“处理中/失败原因/重试”，不伪装成没有资料。来源定位失败时打开文件并说明暂不能定位，不跳到不相关段落。

## 6. 时间轴与可视化

### 6.1 一个患者，一条统一时间轴

时间轴回答“什么时候发生了什么、目前处理到哪一步、依据在哪里”。默认最近事件在前，先展示有限条数，展开/分页查看全部。提供事件类型、日期范围和关键词筛选。

| 事件类型 | 应展示的内容 | 点击后的结果 |
| --- | --- | --- |
| 就诊 | 日期、机构/科室（已有时）、事由和摘要 | 对应病历 |
| 检查 | 检查日期、项目数量、主要记录 | 报告或指标详情 |
| 用药 | 确认的开始/调整/停用；或明确标注历史记载 | 药物变更记录和依据 |
| 监测 | 血压、体重等患者上报值 | 对应记录或趋势选中点 |
| 随访 | 联系、反馈、处理结果和下一步 | 随访事项详情 |
| 消息 | 需要处理的患者消息或消息组 | 对应会话位置 |
| 资料/修订 | 导入、核对和修订 | 文件、差异或审计详情，默认可折叠 |

日期不明的事件进入“日期待核对”，不能用导入日期冒充就诊日期。未来随访放在“后续安排”，不混入已经发生的历史事件。多份文件复述同一次就诊应关联来源，不复制成多个就诊事件。

点选事件打开详情和来源；关闭后保留筛选和位置。逐条消息不应淹没临床进程，可按一次随访会话聚合，展开看完整原话。

### 6.2 指标图规则

- 血压使用同一 mmHg 轴的收缩压/舒张压两条序列，以颜色、线型、文字三种方式区分。
- 检验只比较同项目、同单位记录；单位换算必须有显式规则及原始值，不能直接拼接不同单位。
- 横轴按真实时间间隔，不按记录序号等距排列。V5 的等距日期仅适用于其示例，正式版沿用真实日期计算。
- 一个有效日期时显示单次结果；无数值/日期/单位时展示原始记录并说明为何不绘图。
- 同日冲突不能静默选一个值。支持完整时间区分或进入核对；核对前展示冲突数据并暂停连线。
- 有中断和缺失时标明间隔，不自动插值。缺测不能填零。
- y轴标注刻度及单位，选取范围避免夸大细小变化。图下始终可查看记录表。
- 参考区间只能来自明确报告/规则，需标明出处及适用记录；没有依据时不涂红绿“正常/异常”。

交互要求：切换指标、选择日期点/记录、查看原文、图表与表格切换、通过 AI 调出指定指标。键盘操作须能达到与鼠标相同的记录。

### 6.3 随访进度可视化

展示“已联系—资料回收—待核对—处理完成/下一次安排”。每步带实际时间或缺失原因，点击进入任务。异常分支包括未联系上、患者暂缓、任务取消、发送失败、需要医生处理。

下一次计划与本轮完成度分开：建立了未来计划不代表本轮已完成。不要用虚构百分比或单一进度条掩盖缺失资料。

### 6.4 P1/P2 可扩展的图

P1 可增加用药变更轨迹、问卷分数趋势、检查/转诊节点；只有具备相应数据时显示。P2 的科研队列图和复杂分析放在研究页面，不挤占每个患者首屏。

## 7. 随访与微信工作流

### 7.1 随访首页

默认使用“事项列表 + 详情”。列表突出患者、要做的事、截止时间、处理状态；详情展示相关原话、资料、最近处理及主要动作。

一级状态为待处理、等待回复、已完成；失败和逾期在待处理中提供明确标签。模板、自动化规则、运行记录在二级入口。

“任务状态”和“消息发送状态”分开记录：点击发送不能自动标记患者已回复，也不能自动结束随访。

```text
计划生效 → 到期生成任务 → 准备内容 → 发送/人工联系
                                     ↓
                            等待回复 / 发送失败
                                     ↓
                        收到资料 → 待核对 → 完成本轮
                                     ↓
                              安排下一次（可选）
```

“完成”需要记录处理结果；后续补充记录不覆盖原记录。重新打开保留历史。计划暂停阻止未来执行，同时明确显示已经生成的任务将如何处理。

### 7.2 最短工作流

1. 医生进入待处理队列，选中患者事项。
2. 看到患者原话、缺失资料及需要做的事。
3. 直接操作，或让 AI 整理资料/起草回复/调整计划。
4. 在当前事项内查看结果，必要时确认临床资料修改或发送内容。
5. 完成后自动定位下一项；患者时间轴同步产生对应事件。

### 7.3 微信接入的产品设计

患者页显示绑定会话、联系对象（本人/家属）、最近同步时间、同步覆盖范围及渠道状态。不要把联系人昵称当作唯一患者标识；同名、家属代管及一人多会话必须能处理。

自动管理规则由自然语言生成可编辑表单，至少包含对象、触发条件、模板、时间范围、频率、安静时段、失败处理和停止条件。保存后能看懂“谁会在什么时候收到什么”，并一键暂停。

低风险提醒可在医生明确授权的规则范围内自动执行；超出规则、身份不确定或涉及临床判断时进入待处理。UI 不为每一次读资料、切页面、改字号增加确认弹窗。

### 7.4 接入路径与状态

用户提供的 [wechat-desktop-automation](https://github.com/JuneYaooo/wechat-desktop-automation) 是 Windows 桌面自动化参考，包含可见消息读取、发送预览及有限规则自动回复。它不提供完整聊天历史读取保证。当前仓库的 `WeChatMacBridge` 面向 macOS，两者应通过共同渠道接口适配，不能直接视为同一实现。

建议统一接口：连接探测、会话匹配、读取可见内容、准备发送、执行发送、检查结果、停止规则。上述名称为接口职责建议，实施时与现有路由对齐。

发送记录至少区分草稿、待发送、执行中、界面显示已发送、结果不确定、失败。桌面 UI 证据不能推断患者已读或送达。结果不确定时先核查，不自动重发。重复触发通过任务 ID 和幂等键抑制。

## 8. 贯穿全系统的 AI

### 8.1 三种显示方式

| 模式 | 布局与用途 | 状态要求 |
| --- | --- | --- |
| 工作区 | 页面为主，底部紧凑输入；适合日常浏览和少量指令 | 不遮挡表格、底部操作及滚动内容 |
| AI 半屏 | 左侧对话、右侧患者/任务/研究；适合协作处理 | 可调整宽度；保存当前对象、选中资料和未提交草稿 |
| AI 全屏 | 对话为主，适合描述复杂需求与回顾执行 | 能恢复上一个工作视图；必要时调出半屏表单 |

根据工作区实际宽度调整，不只根据整个窗口宽度。窄屏使用“对话/工作内容”切换或纵向布局，不能把病历压到无法阅读。切换模式不能重新请求执行动作或清空对话。

### 8.2 AI 能操作到什么程度

“通过 AI 完成一切工作”应落实为：每个业务操作均有可调用、可校验、可反馈的动作；每个页面与资料位置均有结构化定位方式。新增功能时同步提供 UI 入口与 AI 动作。

| 类型 | 示例 | 建议执行方式 |
| --- | --- | --- |
| 导航与读取 | 打开陈女士、查看9月检验、筛选待随访患者 | 直接执行并定位 |
| 个人 UI 偏好 | 字放大、用药置顶、切半屏、隐藏已完成事项 | 直接修改配置，可恢复默认 |
| 草稿与任务 | 生成随访计划草稿、整理病程 | 展示可编辑结果，不冒充已生效 |
| 临床字段修改 | 核对过敏史、修改用药状态 | 展示原值、新值和依据，确认后保存 |
| 对外发送 | 回复患者、开启提醒规则 | 展示具体对象、内容、范围；按单次授权或既有有效规则执行 |
| 科研操作 | 筛选队列、核对字段、生成分析 | 展示条件、数据版本、方法和可追溯结果 |

UI 配置属于可支持的结构化修改。任意生成代码并重写生产界面不是 P0 的“AI 改界面”实现方式；需要新组件或新业务能力时进入开发流程。

### 8.3 统一动作流程

```text
按钮/表单 ─┐
           ├→ 动作目录 → 参数与权限校验 → 读取或执行/生成提案
AI 对话 ───┘                                      ↓
                       结果事件 ← 业务持久化 ← 确认（需要时）
                          ↓
              更新页面 + 定位结果 + 时间轴/审计 + 对话反馈
```

每条指令必须绑定对象。AI 显示“当前患者：陈女士”，可以显式添加文件/指标/研究作为上下文。用户切患者时，未完成动作继续绑定原患者；不可沿用新的当前患者 ID 执行旧动作。

长任务显示正在读什么、已完成什么、剩下什么、是否可取消。失败说明可恢复步骤；动作未成功就不能回复“已完成”。模型不可用时，患者浏览、人工编辑和随访处理仍可工作。

示例：输入“把下次随访改到周五上午九点”，先解析当前患者、现有计划、实际日期和时区，再展示修改结果；若有多个有效计划，选择具体对象后再执行。

## 9. 诊疗辅助与科研

### 9.1 诊疗辅助嵌入患者页

P1 在患者上下文提供病程整理、缺失/矛盾发现、药物资料核对、指南和文献检索、问诊或随访问题建议。输出由“任务—结果—依据—待核对事项—下一步”组织。

资料事实与模型推断分层展示，引用可定位来源。输出可以作为草稿保存到患者资料，但不能把模型生成段落直接当作原始病史。已有相关功能迁移时保留入口，不因调整导航而丢失。

### 9.2 科研由患者管理数据延伸

目标流程：研究问题 → 纳排条件 → 候选队列 → 字段与来源核对 → 数据集版本 → 分析 → 导出。研究纳入不因一句“这些人符合条件”就自动全部确认。

研究首页以项目列表为主，打开项目后显示受试者表格。常用列：研究编号、纳入状态、基线、随访、缺失字段和待核对数量。点击缺失直接进入字段及来源，不停留在统计数字上。

字段核对视图包含当前值、原始来源、建议值、核对状态和变更记录。修改研究派生变量不默认反写临床档案。

复用现有 CSV 分析、描述统计、检验和样本量功能；新增研究对象与数据快照后再联动。图表需要显示样本范围、缺失处理、方法、数据版本和运行时间，不能只给“AI 结论”。

去标识导出至少预览列清单、自由文本和映射策略。研究编号通常仍需受控关联，不能把移除姓名等同于完全匿名。

## 10. 视觉、交互与适老化

以下是实现起点，需用真实工作任务测试调整；不是已经达到的指标。

| 项目 | 建议规范 |
| --- | --- |
| 配色 | 沿用浅色背景、白色内容区与墨绿主操作；语义警示色少量使用 |
| 正文字号 | 16–18 px；病历阅读推荐18 px；大字模式20–22 px |
| 辅助文字 | 重要日期、单位、状态不低于14 px；不继承原型过小的说明字 |
| 点击目标 | 高频操作建议至少44×44 px；紧凑表格仍保留足够命中区域 |
| 行高 | 中文连续阅读1.7–1.9，表格适当紧凑但不拥挤 |
| 内容宽度 | 正文控制单行长度，宽屏用于对照而非无限拉长段落 |
| 层级 | 页面标题、栏目标题、正文、辅助说明四级；避免每段都变卡片 |
| 表格 | 数值使用等宽数字；表头清晰；单位常驻；状态不只靠颜色 |
| 动效 | 简短状态反馈；尊重减少动态效果设置；不滚动劫持 |
| 键盘 | Tab焦点可见，筛选、图表记录、阅读器、表单皆可操作 |
| 布局 | 用可用容器宽度决定并排/纵向，避免 AI 半屏挤压内容 |

默认患者信息区宽度足够时可并排图表和时间轴；更窄时纵向。原文阅读优先保证可读宽度，必要时取代档案内容而不是第三列叠加。

一屏只有一个强调主操作，例如“处理随访”或“保存修改”。不用每个区域都放大号“AI 分析”按钮；全局对话即可覆盖多数操作，局部 AI 入口只在明确选中对象时出现。

读资料时不要频繁弹窗。局部修改用行内表单或侧栏，只有跨对象批量变更、临床字段提案和发送范围等需要明确确认的动作使用确认界面。

## 11. 数据与工程契约

以下字段是建议契约，需要与现有服务及迁移方式对齐，并非当前 API 清单。

### 11.1 患者事件与来源

| 对象 | 建议字段 | 约束 |
| --- | --- | --- |
| PatientEvent | id、patientId、type、occurredAt、recordedAt、datePrecision、title、status、sourceRefs、relatedTaskId、revision | 业务发生时间与录入时间分开；支持未知日期 |
| SourceRef | fileId/messageId、page、textRange、原文片段、版本 | 能打开具体依据；来源不存在时显式标记 |
| Observation | patientId、item、value/rawValue、unit、observedAt、referenceRange、sourceRefs、verificationStatus | 保存原值；同单位比较；不把缺失当零 |
| MedicationRecord/Event | 药物、剂量、频次、状态、起止时间、记录/变更类型、来源、确认者 | 历史记载与真实变更分开 |
| FollowupTask | patientId、planId、dueAt、timezone、owner、status、outcome、nextTaskId | 任务与消息状态分离 |
| ChannelMessage | channel、conversationId、patientBinding、direction、contentRef、observedAt、deliveryEvidence、taskId | 绑定可核对；保留采集范围 |
| ViewContext | page、patientId/studyId、tab、filters、selection、sourceRef、displayMode | 不承载临床事实；切换显示不触发业务写入 |

事件优先从已有就诊、检验、消息和任务派生，并保持原实体 ID 关联；补充人工事件再新增记录。时间轴和详情不要各存一份不一致的业务数据。

### 11.2 动作目录

建议的动作职责包括：打开患者、设置视图、打开来源、查询时间轴、查询指标、创建随访草稿、更新计划、完成任务、提出临床字段修改、确认提案、准备/发送消息、暂停规则、筛选研究队列。

每个动作声明参数 schema、对象范围、读写类型、所需能力、是否需要提案/确认、幂等键及结果事件。返回至少包含状态、对象 ID、变更版本、结果定位和错误信息。

临床写入延续 expectedRevision 等并发保护。旧版本提案不能覆盖新数据；提示重新对照，保持用户草稿。撤销按新修订记录实现；已发送消息不能伪装为可撤销本地修改。

### 11.3 一致性与恢复

- 同一修改在患者档案、任务列表、图表、时间轴和对话结果中一致更新。
- 重载后保留已保存数据；未保存草稿有明确标记和恢复策略。
- 重复点击或 AI 重试不能重复建任务、发消息或入组。
- 切换患者时隔离来源、图表筛选、草稿和异步响应。
- 连接失效、模型超时、文件解析失败、权限变化都有明确状态与恢复动作。
- 消息、文件内容只作为业务输入，不能作为扩大权限或改变执行规则的指令。

| A07 | 点击图下记录查看原文 | 指标、日期、患者与原文一致 |
| A08 | 编辑随访、完成、重新打开 | 任务列表、详情、时间轴一致，刷新后保留 |
| A09 | 模型离线 | 人工浏览与操作仍可使用 |
| A10 | AI 打开时间轴和检验 | 正确患者、正确页面、对话上下文不丢 |
| A11 | AI 修改临床字段 | 有差异与依据；版本冲突不覆盖 |
| A12 | 三种显示模式和大字 | 保留草稿、筛选、来源位置；重要控件可见 |
| A13 | 微信会话身份不确定 | 不误绑定/误发送，能进入核对 |
| A14 | 发送结果不确定、重复触发 | 不盲目重发，有状态和追踪记录 |
| A15 | 自动规则过期/暂停 | 不再触发新发送，已在执行的动作有明确结果 |
| A16 | 研究字段核对和导出 | 有来源和版本，临床档案不被静默反写 |
| A17 | 资料解析失败或来源不可定位 | 能看原文件、理解原因并重试 |
| A18 | 临床辅助引用失效 | 不展示为已核实证据，保留待核对状态 |

### 13.2 适老化任务测试

建议邀请5–8位医生，其中包含不熟悉复杂软件的资深医生。无需解释页面，分别完成：找到患者过敏史、查看最近检查原文、理解最近一次随访、修改下次时间、通过对话打开指标图、返回完整档案。

记录任务完成率、耗时、误点击、求助次数和关键状态理解错误。建议初始目标：主要任务无需指导完成率≥90%；找到最近检查原文的中位时间≤15秒；常用任务无需经过三级以上菜单；测试场景中患者错配为0。以上是待验证目标，不是已测结果或可靠性保证。

视觉验收覆盖大屏、普通笔记本、窄窗口、AI半屏和大字模式；不能只看一张宽屏截图。
