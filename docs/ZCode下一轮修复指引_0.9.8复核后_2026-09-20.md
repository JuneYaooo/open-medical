# ZCode 下一轮修复指引：可信评测与真实交付闭环

基线：`798cd75`（0.9.8）。前次版本：`2cb3182`。本任务书依据《代码复核_0.9.8_2026-09-20.md》，细化总路线的 W3/W4/W5/W9，**本轮只修下述缺陷，不要求重写整个系统或完成所有 L3 认证**。用户后续明确指令优先。

## 1. 本轮必须达到的结果

1. 评测时，模型生成的代码不能接触答案、评估控制器、宿主凭据或工作区外数据；失控代码能在预算内结束。
2. 必需检查未通过或未运行，绝不能进入成功率分子。报告不能同时宣称“通过”又附带关键检查 blocked。
3. 通用工作区与医疗入口的真实运行都使用交付契约，只有目标要求的成果得到验证，才显示“已交付”。
4. 正式评测能使用项目已保存的模型配置；多轮任务统计与预算覆盖整个任务，而非只覆盖首轮。
5. 新增反例能稳定复现修复前问题，修复后通过；保留正常问答、合法工具执行和既有工作区体验。

不以“新增接口/字段”“单元测试全绿”“完成了一次工具调用”替代以上结果。不扩大到医疗新功能、复杂团队重构、全新 UI 或外部框架替换。

## 4. N1：修复验收器的宿主执行逃逸

### 4.1 问题与证据

`scripts/eval-v1/validators.mjs` 的 `runNode` 使用宿主 `spawn(process.execPath, ...)`，`importRunner` 导入模型生成的 C01—C04 模块。子进程继承仓库工作目录、环境与宿主权限，没有执行隔离或超时。

复核探针让 C01 的 price.mjs 读取仓库 `evals/general-agent-v1/cases.json`，确认 oracle 可见，再返回正确 total 函数；验收仍 pass。探针只读公开合成数据，没有读取秘密。模型代码还可通过无限循环、残留定时器或子进程使验收挂起。

相关入口一起检查：`validators.mjs`、`lib/fixtures.mjs` 的 hashTree、`lib/browser-check.mjs`、现有受控执行后端。hashTree 当前使用 statSync 跟随符号链接，不能把字符串相对路径检查当作真实文件边界。

### 4.2 必须实现

- 引入/复用评估专用的受控执行接口，在实际隔离边界内运行产物。评估控制器持有答案；被测环境只获得任务材料、待测产物和运行所需最小资源。
- 优先复用项目已经具备、经验证的沙箱后端。容器仅挂载测试工作区，不能挂载仓库、用户目录、Docker socket；不继承宿主模型密钥。代码断言默认不需要网络，按最小必要能力运行。
- 后端不可用时明确 blocked；不得静默回退宿主 Node。设置 cwd、清空少数环境变量、字符串路径检查、单独使用 vm 都不能当作 OS 隔离的证明。
- 对子进程/容器设置实际截止时间、输出大小上限和取消清理；超时后清理其子进程/容器，报告 timeout。不得仅终止一个父进程而留下工作进程。
- 评估控制器收集产物时使用 lstat/realpath 或等价机制检查边界，拒绝跟随工作区外符号链接/junction；防目录循环、过大输出和读取时路径替换。不能直接把未验证的路径交给宿主解析器。
- 固定待测产物快照或记录执行前后哈希。若被测模块在检查中篡改产物，应作为异常记录；不能在验收后继续沿用执行前的文件清单。
- 被测代码不得自行输出“断言通过”就被采信。断言结果由可信控制器产生，避免伪造 `__RESULT__` stdout 或篡改沙箱内测试文件影响判定。明确区分被测程序输出与控制协议。

### 4.3 验收用例

| ID | 输入/故障 | 预期 |
| --- | --- | --- |
| N1-01 | 合法 C01/C02 修复 | 真实隔离后端执行成功，数值与不变性正确 |
| N1-02 | 模块尝试读取评估答案或工作区外合成诱饵 | 读取被拒/不可见，不能因正确返回值掩盖越界 |
| N1-03 | 模块枚举环境变量 | 测试注入的宿主秘密哨兵不可见；不使用真实密钥 |
| N1-04 | 无限循环或永久定时器 | 到期限结束，timeout，无残留任务 |
| N1-05 | 大量 stdout | 输出被有界处理，控制器不耗尽内存 |
| N1-06 | 文件符号链接/junction指向外部，或目录自环 | 不读取外部内容、不递归挂死；缺 OS 权限时对应真实用例 blocked |
| N1-07 | 后端不可用 | blocked，不执行宿主 fallback |
| N1-08 | 模块伪造结果标记/修改测试文件 | 不影响可信断言，不被误计通过 |

验收器与实现模型仍共享整个仓库时，只能说开发集可见，不能宣称隐藏集隔离；私有留出继续由独立评估方维护。

## 5. N2：必需检查 blocked 不能计为通过

### 5.1 问题

`validators.mjs:finish` 无条件包装 `status:'pass', pass:true`。S04 明确返回“独立公式引擎重算 blocked”，D01 返回“版式渲染 blocked”，却仍被 run.mjs 计入 pass。S04 已动态复现。

### 5.2 必须实现

- 用明确的检查项结构，例如 `{id, required, status, reason, evidence}`。检查状态至少区分 pass/fail/blocked；timeout 和执行异常另行记录。
- 必需检查全部 pass 才能任务 pass；任一必需检查 fail 则 fail；无确定失败但有必需检查 blocked 则 blocked。实际超预算为 timeout；需要额外人工救援不得算独立成功。实现时写出确定的聚合规则与优先级，避免不同出口各自判断。
- 可选检查的提示不阻断任务，但 required/optional 必须在数据版本中事先确定，不能根据候选输出临时改。
- S04 的独立引擎重算和 D01 的版式检查仍为必需项。小型自写公式求值器、仅解析 XML 可作为部分检查，不能替代这两项。可检测已安装可用工具；缺失时保持 blocked。
- 汇总、退出码、Markdown/JSON报告使用同一聚合结果。正式认证有必需 blocked/timeout 时不得 exit 0；确需区分基础设施自测模式，单独标记，不改变正式认证语义。
- 修正现有自测对“正确产物即应 pass”的假设：缺少必需环境时应断言部分检查 pass、任务 blocked。需要全通过样例时使用显式测试适配器并标记 mock，不能冒充真实渲染或重算。
- 90次基础分母固定，故障与变体另计；不能丢掉 blocked 来提高成功率。出现多种失败原因时保留全部检查明细。

### 5.3 验收

S04 无独立引擎时 blocked、有正确引擎且初始74/修改后49时pass、硬编码总额时fail。D01无渲染通道时blocked、结构正确但渲染明显重叠时fail、结构与渲染通过才pass。汇总包含一项pass与一项blocked时成功数为1、分母为2；不能显示100%。必需检查故意省略应视为未完成，不默认通过。

## 6. N3：把交付契约接入通用真实执行路径

### 6.1 问题

`AgentRuntime` 新增 onDelivery，但 `WorkspaceService.execute` 没有传入，完成落库也没有消费 result.delivery/outcome。通用任务仍直接 completed、发完成事件与通知。SessionBridge 只能投影已有字段，无法补足缺失验证。

合成模型直接声称 report.txt 已创建，零工具调用，文件不存在；实际 WorkspaceService 返回 completed，delivery/outcome为空。此缺口在账本中已有记录，但必须在本轮接通。

### 6.2 契约与实现要求

1. 先记录现有任务/run/事件/UI消费者，定义最小任务结果契约。区分纯回答与执行交付，不用“是否调用过工具”决定任务类型，也不能只依赖模型自报的类型。
2. 对明确执行目标记录可核对要求与目标版本，例如需要创建的文件、必要外部动作、必要验证；无法确定要求时按任务需要澄清或标记尚未验证，不能默认交付。目标提取可用模型辅助，但证据必须来自运行时事实。
3. 一个一致的最小结果结构应能表达：适用性、目标版本、逐项必要要求、已核实证据、缺口、检查异常、结果分类。复用现有字段或兼容扩展，避免新增两套 delivery schema。
4. 把验证钩子真正接进 WorkspaceService、持久化 run、完成事件、查询接口/publicWorkspace、SessionBridge与前端。恢复后仍能看见相同事实，不只在当前 SSE 中临时显示。
5. 验证结果不完整时：预算允许且有可操作缺口，可反馈给执行循环继续修正；明确受环境阻塞则 blocked；运行结束但交付失败应报告失败及缺口。**不要把执行任务未完成降格为 answered+completed 来绕过要求。** answered 保留给目标本来就是回答的任务。
6. 如果为了兼容确实要保留旧 status=completed 表示“轮次结束”，必须另有明确的任务结果状态供所有UI/通知/恢复消费；缺口不得展示为成功。提交此兼容映射说明，不允许客户端各自猜测。
7. 验证钩子抛错：执行类任务持久化 unverified/blocked/failed 与原因，不再返回null丢失事实。普通问答不因缺少文件验证器而失败。验证过程响应取消，取消后不能晚到写成成功。
8. 证据关联 task/run、要求、路径或回执、版本/哈希和验证时间；旧文件存在不自动证明本次创建/更新成功。已有文件可合法作为输入，不能一概禁止复用。
9. normalizeDelivery 不能接受自相矛盾的 delivered:true + 必需缺口，不能把失败回执或任意object当作充分证据。其职责是校验契约，具体语义验证由对应验证器承担。

### 6.3 必测链路

| ID | 场景 | 预期 |
| --- | --- | --- |
| N3-01 | 普通问答、零工具 | 正常回答，不强制生成文件 |
| N3-02 | 要求创建文件，模型只说完成 | 文件缺失被识别；不成功交付；缺口持久化 |
| N3-03 | 正确创建并检查文件 | delivered，证据对应本次产物 |
| N3-04 | 要求两份产物，只完成一份 | 列出未完成项，不能delivered |
| N3-05 | 已存在旧文件，模型没执行要求的更新 | 不把旧文件当作更新完成 |
| N3-06 | 验证器异常/超时 | 保留明确未验证状态，不静默回退成功 |
| N3-07 | 验证期间取消 | 最终取消，晚到验证不覆盖状态 |
| N3-08 | 页面重载/服务重启 | 查询、事件和UI显示一致结果 |
| N3-09 | 执行中修改要求 | 依据最新有效目标版本核对，不沿用旧验证结论 |

至少跑一个通用服务API集成用例和一个真实浏览器UI用例；只测 AgentRuntime 的钩子函数不够。

## 7. N4：医疗交付不能等同于发生过副作用

### 7.1 问题

`server/runtime.mjs` 无论子代理成功或失败，都向 delegatedReceipts 添加记录；onDelivery 又把 artifacts/sandboxReceipt/delegatedReceipts 任一存在作为 delivered:true。全部子任务失败且没有产物，仍能走成功分支；无关沙箱执行也会被当作完成目标。本问题已由代码分支确认，本轮实施需补动态回归。

### 7.2 必须实现

- 和N3共用结果语义与校验层，旧医疗runtime只是领域适配，不另建状态体系。
- 每条子任务回执记录真实状态与有效产物引用。失败回执保留作诊断，不能作为成功证据；子任务status=completed也不自动代表父目标全部完成。
- 沙箱成功只证明该动作成功，必须映射到相应目标要求；无关执行不能抵消缺失产物。
- 结构化医疗草稿需要按要求检查必要字段、来源和状态；有artifactId/hash只证明对象存在，不证明内容满足任务。
- 多项要求逐项核对；产物awaiting review可显示“草稿已生成、待复核”，不能宣称医生已确认或患者操作已生效。
- 纯咨询、明确生成草稿、待医生审批的外部动作分开处理；不能为通过交付判断自动确认医疗提案。

### 7.3 验收

子任务全部失败→无交付；一个成功一个必要失败→部分缺口；无关沙箱成功→目标仍未完成；有效草稿→草稿可查看且标记待复核；全目标通过→准确交付。上述至少两项穿过实际 MedicalRuntime执行链路，另验证SessionBridge的主医疗入口，避免只修已不常用的旧路径。

## 8. N5：统一模型配置发现，正式评测能独立启动

### 8.1 问题

verify-model 有配置发现，eval-v1/run.mjs 直接createProvider，后者只读进程环境。单独跑verify-model所加载的.env不会传到另一个命令进程，因此把配置放进model.env后照说明运行评测，仍可能报无配置。

### 8.2 必须实现

- 抽出无副作用的配置解析/发现模块，共用到 verify-model、eval-v1 和适用的现有入口。不要import一个执行型脚本来顺便加载环境。
- 核对desktop实际保存/发现位置，支持真实桌面配置与仓库.env；不要仅复述现有注释，先检查实现。
- 明确优先级并输出脱敏来源：显式运行参数（若支持）→有效进程配置→项目桌面配置→仓库配置，或沿用项目已有一致规则。不能因为仅有AI_PROVIDER而忽略其余有效保存配置，也不能把不同提供方的key/baseURL/model拼在一起。
- 配置校验完整后才判断configured；本地无密钥模型是合法情形。错误文件要报告错误，不能静默切换到另一账户发起请求。
- 报告可含provider/model与配置来源类别，不能包含apiKey、Authorization、URL内凭据或完整.env；异常日志也要脱敏。
- 不要求改变用户现有桌面配置，不修改或复制其他应用凭据。

### 8.3 验收

以全新子进程覆盖：仅临时桌面配置、仅临时.env、完整环境覆盖、仅provider环境+保存配置、冲突提供方、损坏配置、无配置、本地无密钥模型。使用临时目录和本地模拟端点测试发现协议，禁止读取测试机真实秘密来断言。真实模型配置可用时再执行1项小规模真实冒烟，之后是否跑完整90次由当前环境与任务范围决定并记录。

## 9. N6：多轮评测的轨迹和预算覆盖整项任务

### 9.1 问题

T01/T03和A01后续轮更新run/finalAnswer，却未更新或聚合runId；正式报告的工具轨迹、tokens、压缩事件仍取首轮。每次runAgent重置600秒/80轮，导致多轮任务实际预算扩大。runNode无限等待的问题由N1一并解决。

### 9.2 必须实现

- 每次数据集试验建立trialId，对应多个runId，逐轮记录输入类型（初始/预设补充/审批决定/恢复）、耗时、tokens、工具调用和副作用。报告同时提供逐轮与整项聚合。
- 整项共享截止时间、模型轮次与工具调用上限。将剩余预算传入每一轮；预算覆盖执行、审批控制器自动动作、恢复、验证与清理的约定必须明确。清理可有额外有限宽限，但不能改变已超时判定。
- max_tool_calls必须真实执行，不能只出现在protocol.json。max_output_tokens_per_call需传到实际模型请求或明确报告不可施加，不能声称已有统一预算。
- 重试消耗同一trial预算。用户预设补充不算额外救援，但其tokens/工具动作必须计费计数；人工临时指导标为assisted。
- 原始base30×3固定90条；A01拒绝变体、T02长变体、X01—X12故障另表统计。当前variants默认全部展开，不能直接用results.length作为基础集分母。
- variant必须验证是否合法；未实现的故障不得仅因传入variant名称而执行普通基线再报告故障通过。
- 每次运行独立report目录或明确attemptId，避免results.jsonl追加历史、summary仅统计本次造成口径不一致。边运行边保存已结束项，崩溃不丢全部证据。
