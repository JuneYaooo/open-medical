# Open Medical 产品形态与核心流程

更新：2026-09-08。本轮已落地到现有 React 界面与运行内核；以下单列后续扩展，避免把设计意图当作已交付能力。

## 产品定位

一个面向医生的个人医疗 AI 工作台。采用 WorkBuddy / BioMed AI 的任务入口思路，把医生的具体工作组织成「选对象 → 准备材料 → 整理生成 → 核对成果 → 继续随访」。

参考：[腾讯健康 BioMed AI 发布文章](https://www.163.com/news/article/L5TA4NIO00019UD6.html)。本项目重点服务病例整理、患者资料与随访；文章中的影像分析、药品数据库、分子设计等没有被包装成可用功能。

## 一级信息架构（已实现）

| 入口     | 用户要解决的问题               | 页面职责                                                                 |
| -------- | ------------------------------ | ------------------------------------------------------------------------ |
| 工作台   | 今天要做什么？                 | 自然语言任务入口、患者选择、场景模板、待复核/到期随访/待办数量、最近工作 |
| 患者档案 | 这位患者有哪些资料与后续安排？ | 建档、分组、病例工作区、消息、随访                                       |
| 任务记录 | 上次做到哪了？                 | 搜索已有工作区，查看执行状态和待复核数量，继续任务                       |
| 待复核   | 哪些成果需要我判断？           | 按工作区汇集 draft 成果，点击优先打开待复核产物与来源                    |

左侧导航在患者和任务之间保持一致。中间是任务内容及执行过程；右侧是材料、成果和执行记录。窄屏将左侧导航和右侧面板收为按需展开。

配置、运行方式和计算工具属于次级操作。计划任务必须有当前任务上下文，不能在首页对未明确的患者误建计划。

## 核心对象与关系

| 对象   | 当前模型      | 生命周期与归属规则                                                        |
| ------ | ------------- | ------------------------------------------------------------------------- |
| 患者   | Patient       | 建档自动建立一个病例工作区；患者是长期上下文                              |
| 工作区 | Session       | 患者工作区关联 patientId；独立任务不关联患者。当前任务列表按 Session 展示 |
| 执行   | Run + Message | 同一工作区可多次执行；每次有自己的输入、材料范围、状态与记录              |
| 材料   | Source / File | 属于工作区，每轮只使用选中范围；来源与页码/行号保留                       |
| 成果   | Artifact      | 默认 draft；复核可以 approved 或 rejected；编辑后重新进入 draft           |
| 随访   | Followup      | 归属于患者，医生设置时间、频率、清单；到期提醒，自动摘要需独立授权        |

重要约定：本轮没有新增一套 Task 数据表。界面中的「任务记录」复用已有会话；患者工作区里的多次执行仍共用一个 Session。后续若引入患者下多个独立任务，需明确新增 Task 层，不能把同一患者的历史资料重复复制到多个无关联会话。

## 入口与场景路由

1. 在首页选择场景或描述需求。点击场景只填入可编辑的任务模板，不自动运行。
2. 选择患者时沿用该患者的 sessionId；不选患者时新建独立工作区，并以场景或需求命名。
3. 「准备任务」进入工作区，保留任务输入。医生添加/选择材料，确认运行方式后才发起执行。
4. 切换工作区会清除上一个工作区的模型授权、任务输入和联合整理选项，默认本地运行；旧的异步响应不能覆盖新工作区。
5. 「安排随访」要求选择患者，直接进入该患者的随访计划页；不创建聊天会话，不把医生引到新建患者表单。
6. 建档是独立且真实的入口，电话与性别可不填；建档完成后进入患者详情。

已提供场景：病历时间线、检验数值摘录、用药资料核对、随访计划、循证检索准备。循证场景交付 PICO 和检索策略；它不表示已联网检索或得到了临床证据结论。治疗方案评估仍从患者详情进入并使用原有模型授权规则。

## 结果与接续

- 用户始终能分辨当前工作区属于哪位患者，且能直接返回患者档案。
- 工作区显示「准备材料 → 整理生成 → 复核成果」阶段提示。实际执行状态仍以 Run 为准。
- 全局待复核数量统计成果的 draft 状态；进入待复核记录优先选择一份 draft，避免打开最近一份已复核成果。
- 从患者详情点击某一成果，直接定位该成果，而非只打开聊天页。
- 核对来源、填写复核者代号与说明后记录结果。approved 成果会露出「安排随访」入口，关联同一患者。
- 随访入口仅复用患者上下文；当前没有把 AI 结论自动写成随访清单，也没有将一次复核当成自动外发授权。
- 保存随访计划、消息等操作后保持当前详情页签，减少重复定位。

## 交互与异常

首页保留真实空状态和加载占位；无患者时随访按钮不可执行。患者/任务列表读取失败可重试。模型调用仍沿用逐次外发授权，失败/中断仍保留运行记录。患者工作区不能从任务侧删除。

移动端提供可展开导航与点击遮罩关闭；进入具体页面后自动收起。字体、结果预览与来源定位优先于装饰。颜色以浅灰白和医疗青绿为主，琥珀色仅用于待复核状态。

## 后续扩展顺序（尚未实现）

1. **患者下的任务层**：每个任务明确目标、负责人（单用户阶段即本人）、产物与完成条件，患者上下文保持连续。
2. **更清楚的材料范围**：病例原件、抽取文字、历史成果分开展示；授权与执行关联到稳定的材料版本。
3. **成果驱动的接续**：医生选定已复核成果，再选择“作为后续任务参考”；保留来源和复核版本。
4. **技能与接入**：先形成有输入要求、可用状态、预期成果的能力清单，再开放专业数据源和连接器。
5. **专病流程**：在已验证的场景上形成专病模板，保留可编辑步骤与人工复核节点。

- 新增 browser-api 集成测试，验证客户端建档、PATCH、DELETE、随访创建、原 JSON 请求形式和 token 过期重试；患者会话列表包含 patientId。

- 真实 Chromium，临时 SQLite + 合成模型：可选电话留空建档、选择患者准备任务、上传合成材料、本地时间线、待复核入口、人工复核、进入同一患者随访、保存随访并停留当前页签。
- 桌面 1440px、移动端 390px 检查；导航可用、无页面横向溢出。
- 预览合成数据与截图位于 output/playwright，不作为产品患者资料。
